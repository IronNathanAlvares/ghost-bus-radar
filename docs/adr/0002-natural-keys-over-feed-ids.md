# ADR-0002: Natural keys, not NTA feed IDs, identify routes and trips

**Status:** accepted, 15 November 2026

## Context

NTA's v2 platform documentation says `route_id` and `trip_id` are autogenerated and regenerated
whenever a new schedule is uploaded, which can be daily. The static feed downloaded on
15 November 2026 confirms the IDs are opaque (`03C_120_e_a`, `10000_GREEN_g_a`, trip `5858_1`),
and that one operator name (Go-Ahead Ireland) appears under two `agency_id`s (`03C` and `3`).
Realtime IDs only match the static feed of the same version.

## Decision

- **Feed version** = `feed_info.feed_version` (a UUID per static publication), with the file's
  SHA-256 as a fallback. Every static table row carries it.
- **Stop** = `stop_id` (NaPTAN AtcoCode). Stable across versions. The public API accepts
  `stop_code` (the plate number on the pole) and maps it.
- **Route** = (`agency_id`, `route_short_name`, `route_type`). `agency_id` rather than name, because
  names repeat across agencies.
- **Trip instance** = (route key, `direction_id`, service date, first departure time,
  first `stop_id`).
- Raw feed IDs are stored, but only ever joined within a single feed version.

## Consequences

- History survives timetable uploads; a route's ghost rate is comparable month to month.
- Joining realtime to schedule must go through the feed version that was live at the event time,
  which the SCD2 timetable tables provide (Sprint 2).
- If two scheduled trips share a full natural key (same route, direction, start and first stop),
  they are genuinely indistinguishable to a passenger; we count them with a duplicate index and
  report how often this happens.
